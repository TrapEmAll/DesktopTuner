# Windows shell integration

## Native Explorer context menu

Windows 11's modern File Explorer context menu accepts general-purpose commands through a packaged `IExplorerCommand` COM class. Desktop Tuner is currently distributed as an unpackaged per-user app, so the bridge uses a sparse identity package that points back to the installed app directory.

The native bridge in `shell/ExplorerContextMenu` registers the same command for selected folders and folder backgrounds. Its menu-construction methods return immediately; invocation resolves the filesystem path and starts `DesktopTuner.exe --open-folder "<path>"`. Windows argument quoting is round-trip tested for drive roots and trailing backslashes. The command DLL is installed beside `DesktopTuner.exe`, as required by its executable-path resolution. The existing single-instance message path then forwards the location to the running app.

The Windows workflow builds the x64 DLL, checks its COM exports, and asks `MakeAppx` to validate the sparse package manifest. It separately checks that the executable, same-directory DLL, and visual assets resolve in the external install layout and that the manifest points to the root-level DLL. Sparse packages keep those files outside the package, so `MakeAppx` skips its package-internal path checks. CI does not register the package or exercise an interactive Explorer context menu.

The optional folder integration also registers per-user verbs for the `Folder` and `Drive` shell classes. Virtual locations such as This PC, Recycle Bin, Network, and Control Panel are passed to `DesktopTuner.exe --open-shell-location` and forwarded to the running companion namespace browser. That same command accepts filesystem folders because Windows can surface both physical and virtual locations through the `Folder` class. While the supervised shell-host is active, Desktop Tuner temporarily owns the `Directory`, `Folder`, and `Drive` default shell verbs, recording and restoring each prior value so virtual-folder activations do not fall back to Explorer. Ownership is transactional: if one class cannot be updated, classes changed earlier in the same attempt are restored before the failure is reported. If Windows sends another folder activation while the supervisor is still starting its worker, the second process waits for the existing Desktop Tuner window for the full bounded startup interval and forwards the request instead of dropping it.

## Replacement taskbar work area

When running as the replacement shell, the taskbar background menu and Taskbar settings both provide an explicit **Exit shell replacement and start Explorer** action. Exiting the worker cleanly lets the supervisor start Explorer for the current session while leaving the saved shell policy available for the next sign-in. The shell-host taskbar disables its close-bar commands so a user cannot accidentally remove every replacement taskbar while leaving the shell worker running.

Edge-docked replacement taskbars register as Windows application desktop toolbars (AppBars). They query and set their approved screen rectangle, reserve that edge from maximized windows, report activation and window-position changes so Windows can coordinate AppBar z-order, yield to full-screen apps, and temporarily hide for Shell cascade/tile operations. When replacement auto-hide is enabled, they also register the selected edge on that monitor with [`ABM_SETAUTOHIDEBAREX`](https://learn.microsoft.com/en-us/windows/win32/shell/abm-setautohidebarex), and release that registration when disabled, moved, or closed. If Windows reports that another auto-hide appbar already owns that monitor edge, Desktop Tuner keeps its local auto-hide behavior and logs a warning. They also respond when the shell reports that taskbar or AppBar positions changed. Closing the taskbar unregisters the AppBar. Floating taskbars do not register because they do not occupy a screen edge and continue to overlay the desktop.

CI verifies the edge geometry and auto-hide eligibility policies, and replacement mode now restores the native taskbar if Windows refuses to register or position an edge-docked AppBar. CI does not launch the custom taskbar or confirm work-area changes interactively. Positioning with a hidden native taskbar, multi-monitor layouts, Windows auto-hide reveal behavior and collisions with the native taskbar, full-screen z-order, cascade/tile handling, cleanup after unexpected process exit, and floating behavior still need validation on supported Windows 11 desktop builds.

This gives each replacement bar a supported taskbar-like work-area contract. In shell-host mode, a display reserves its own AppBar work area whenever that display does not expose an integrated Explorer notification area; another display can continue exposing Explorer's tray without disabling reservation elsewhere. `Win+B` selects the bar on the foreground window's display and focuses its custom tray control first when the native tray is unavailable, while clicking a tray control focuses that specific bar. The shell-host Power User menu provides a bounded **Restart shell replacement** action and the confirmed **Exit shell replacement and start Explorer** recovery action. It does not make the replacement bar the Windows shell, replace native Start visuals, or provide all built-in taskbar and tray behavior.

## Replacing Explorer as the logon shell

Windows [Shell Launcher](https://learn.microsoft.com/en-us/windows/configuration/shell-launcher/) can start a Win32 or UWP application in place of `Explorer.exe`. Microsoft supports it on Enterprise, Education, and IoT Enterprise editions; it is an optional Windows feature, and a shell assignment takes effect at sign-in. Shell Launcher v2 is a whole-shell transition, not a taskbar customization API. Its return-action mapping can restart a shell when it exits.

Desktop Tuner now has an opt-in `--shell-host` runtime mode for use as a per-user Shell Launcher target. That entry point stays alive as a supervisor and runs the interactive shell in a separate worker process. Folder and virtual Shell location requests received while that worker is starting are held and forwarded after readiness; additional activations that arrive in separate processes during that interval wait on the existing worker window and are forwarded too. It starts the desktop host, brings up companion taskbars on every connected display, supplies the custom Start menu and settings window, routes the Windows key and `Ctrl+Esc` to the custom Start menu, and leaves Explorer taskbar controls unhidden. The supervisor temporarily assigns the per-user Directory shell default to Desktop Tuner's folder verb, so external folder activations enter companion Explorer while the replacement shell is active; it records the prior verb and restores it only when Desktop Tuner still owns the setting. A later normal Desktop Tuner launch also removes an orphaned owned verb left by an interrupted supervisor, while shell-host workers preserve it for their active supervisor. If an Explorer notification area is already running, the custom bars expose the best matching notification area on each display and use the native taskbar work-area reservation; when Explorer is absent, edge-docked taskbars request per-monitor AppBar work areas so maximized windows remain clear of Desktop Tuner. The shell host rechecks for Explorer's notification area while running and switches between native tray exposure and custom controls, registering or releasing its AppBar reservation to match. If Windows declines the reservation, the taskbar logs a warning and continues as an overlay. When Explorer is absent, clicking the custom Network or Battery control opens Windows Quick Settings, with direct Network and Power settings available from each control's context menu. `Win+T` and `Win+Shift+T` cycle taskbar controls forward or backward, continuing across connected displays in primary-first order; arrow keys continue navigating within the active taskbar. `Ctrl+Shift+Esc` remains available for Task Manager. In shell-host mode, `Win+E` always opens Desktop Tuner Explorer; outside that mode the shortcut remains an opt-in preference. For the first nine pins, `Win+number` activates the pin, `Win+Ctrl+number` activates its most recently active window, `Win+Shift+number` launches another instance, and `Ctrl+Win+Shift+number` requests an elevated instance when supported. The companion settings window stays available from the custom taskbar and hides instead of closing the shell process. Filesystem folders, This PC, and Recycle Bin opened from the custom desktop route into Desktop Tuner Explorer; other discovered namespace folders open in its companion namespace browser, which displays Windows Shell icons and provides Details/List/small, medium, and large icon/Tile layouts, nested navigation, Back/Forward/Up, address entry, recursive search with Explorer filters and cancellation, extended selection, native Properties from the item menu or Alt+Enter, and combined native context menus for selected items in the same Shell folder. Filesystem-backed Start places and folder flyout entries also use companion Explorer, while Network and Control Panel open in the namespace browser. A normal Exit starts Explorer. The worker signals readiness after replacement taskbars are created, work-area setup has been attempted, and a taskbar has rendered its first frame; if no signal arrives within 60 seconds, the supervisor terminates the worker and retries once. After becoming ready, the worker sends a UI-thread heartbeat every 10 seconds; if the supervisor misses heartbeats for 45 seconds, it restarts the worker once, then starts Explorer if recovery fails. The supervisor exits normally after starting Explorer, so Shell Launcher does not loop-restart a shell that has already failed. If the per-user Custom User Interface policy still points to Desktop Tuner after both worker attempts fail, Desktop Tuner clears that setting so the next sign-in uses Explorer.

### Windows 11 Pro alternate-shell policy

Windows 11 Pro also supports Microsoft's per-user **Custom User Interface** policy, separate from Shell Launcher. The [ADMX WinLogon policy documentation](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-winlogon#customshell) lists Pro, Enterprise, Education, and IoT Enterprise for this user-scoped policy and says Windows starts the specified interface instead of Explorer. This provides a supported Pro route without enabling the Shell Launcher optional feature; it does not add Shell Launcher's configured restart actions or kiosk controls. Home is not listed as supported.

On Windows 11 Pro, Taskbar settings now offer **Use Desktop Tuner at sign-in** and **Restore Windows Explorer** for this per-user policy. Setup writes the installed executable path only when no other custom shell is configured; restore removes that value only while it still points to Desktop Tuner. The same policy can be configured manually in Local Group Policy Editor under **User Configuration > Administrative Templates > System > Custom User Interface**, with **Interface file name** set to the full path of `DesktopTuner.exe` (without command-line arguments). At sign-in, Desktop Tuner detects that the current-user policy targets its own executable and runs its bounded supervisor. A normal shell exit starts Explorer for the current session. If two worker starts fail, including a worker that hangs before signaling readiness, the supervisor restores Explorer for the session and clears the per-user setting only if it still targets Desktop Tuner, preventing the same failed shell from being selected next sign-in. Changes take effect at the next sign-in.

Before testing, keep a separate administrator account available and save work. The supervisor falls back to Explorer if the shell exits normally or fails twice. For manual recovery, use Ctrl+Alt+Delete, open Task Manager, choose **Run new task**, and start `explorer.exe`. Then use Desktop Tuner's **Restore Windows Explorer** action or run `gpedit.msc` and set **Custom User Interface** to **Not Configured** or **Disabled** before signing out and back in. This policy path and the app's detection/supervision are covered by source review and automated tests, but actual logon, crash, and recovery behavior still requires validation on a Windows 11 Pro desktop. Do not use it as a daily shell until that validation is complete.

On licensed Enterprise, Education, and IoT Enterprise devices, Taskbar settings also offer **Configure Shell Launcher for this user** when the Windows optional feature is available. The elevated setup checks both the optional features and the device license, targets only the current user's SID, and refuses to overwrite enabled or pre-existing Shell Launcher mappings. It saves the previous default shell and enablement state, sets Explorer as the default for other accounts, assigns Desktop Tuner only to the current user, and enables Shell Launcher. Restore removes the Desktop Tuner mapping and restores the saved default and enablement state only while those values still match; if another Shell Launcher mapping or a changed default is detected, Desktop Tuner leaves Shell Launcher enabled for manual review. Enabling the optional Windows feature remains a separate administrator action. Test with a non-administrator account and retain an administrator account that remains on Explorer.

## Home/Pro shell overlay

The all-edition shell overlay is available from **Start all-edition shell overlay** in Taskbar settings, or by launching `DesktopTuner.exe --shell-overlay`. It starts the custom desktop, Start menu, and taskbars on all connected displays and routes the Windows key and `Ctrl+Esc` to Desktop Tuner Start. The custom taskbar overlays Explorer's main taskbar controls while leaving the native notification area and third-party tray icons available on supported edge-aligned layouts; the native taskbar continues to reserve the work area. Other layouts may overlap the notification area and use Desktop Tuner's own tray controls. `Ctrl+Shift+Esc` remains available for Task Manager. Explorer stays running in the background with its desktop and shell services, so this is a session overlay, not a Winlogon shell replacement. Enable **Start the shell overlay automatically when I sign in** in Taskbar settings to create the Startup shortcut with this launch mode. Use **Exit shell overlay and return to Explorer** in Taskbar settings or choose Exit from the taskbar menu to stop Desktop Tuner and reveal Explorer's taskbar controls again.

The overlay is experimental. Explorer remains visible and continues to reserve the work area; Desktop Tuner does not hide or change Explorer's taskbar visibility in this mode. It does not prevent users or applications from starting Explorer, and it does not replace native Explorer windows, shell services, or every Windows flyout.

The shell-overlay runtime path is experimental and does not configure Windows. Shell Launcher configuration requires an administrator and a supported edition; the Windows 11 Pro per-user Custom User Interface policy is configured separately through Local Group Policy or Desktop Tuner settings. A managed-edition test must use a separate, retained administrator account that remains on Explorer; target only a non-administrator test account. Keep Ctrl+Alt+Delete available for signing out, and test the rollback path before using it as a daily shell. Do not assign Desktop Tuner as the default shell or to a broad user group.

For a manual test on a supported Windows edition, install Desktop Tuner in the non-administrator test account so its per-user installation is readable there. Then enable the optional **Shell Launcher** Windows feature and use an elevated PowerShell session to add a per-user mapping. Replace the SID and executable path with values for the test account; do not use the elevated administrator's `%LOCALAPPDATA%` path:

```powershell
$testSid = "S-1-5-21-REPLACE-WITH-TEST-ACCOUNT-SID"
$executable = "C:\Users\TEST-ACCOUNT\AppData\Local\Programs\DesktopTuner\DesktopTuner.exe"
$shell = "`"$executable`" --shell-host"
$shellLauncher = [wmiclass]"\\localhost\root\standardcimv2\embedded:WESL_UserSetting"
# Return code 0 means the supervisor started Explorer after Exit or worker recovery.
# Worker crashes are retried by Desktop Tuner; DefaultAction 0 restarts the supervisor if it crashes.
$shellLauncher.SetCustomShell($testSid, $shell, @([int]0), @([int]3), 0)
$shellLauncher.SetEnabled($true)
```

Sign out and back into the test account for the mapping to take effect. The mapping sends a normal exit code of `0` to action `3` (do nothing), while the default action `0` restarts the shell after an abnormal exit. Desktop Tuner starts Explorer before returning `0` from its Exit action. To roll back the test account mapping from an elevated PowerShell session, remove it and sign out/in again:

```powershell
$testSid = "S-1-5-21-REPLACE-WITH-TEST-ACCOUNT-SID"
$shellLauncher = [wmiclass]"\\localhost\root\standardcimv2\embedded:WESL_UserSetting"
$shellLauncher.RemoveCustomShell($testSid)
```

The desktop host spans the Windows virtual desktop, reads per-monitor images and placement from the documented Windows `IDesktopWallpaper` interface, applies the selected wallpaper placement and background color, and refreshes on desktop preference changes plus a 30-second slideshow poll. Dragging over desktop items draws an Explorer-style selection marquee; Ctrl-drag toggles the intersected items. Keyboard users can move between desktop icons with the arrow keys, open the focused item with Enter, show native properties for the selected items with Alt+Enter, rename filesystem items with F2, and open an item context menu with Shift+F10. Namespace items continue to use native Shell context verbs. It persists icon positions independently in monitor-local layouts keyed by display name; if a display disconnects, its icons move to the primary monitor while retaining local coordinates. It enumerates root virtual entries from the Windows desktop namespace, listens for recursive Shell change notifications to refresh virtual items and icons, and supports moving filesystem and virtual Shell icons, including mixed selected groups. Dragging any selection outside the desktop uses a native Shell `IDataObject`; shared-parent selections use the provider's native object, while cross-parent and mixed filesystem/namespace selections use a desktop-rooted Shell data object containing the absolute item PIDLs. It supports multi-select native context menus when selected items share a Shell folder, but does not render child namespace contents inside its own desktop view. The namespace browser exposes the active Shell folder's native background menu when right-clicking empty space and registers for recursive Shell notifications to keep the current folder or search results current; use Refresh, F5, or Ctrl+R if registration is unavailable. Namespace browser items can be dragged to external drop targets through the native Shell `IDataObject`, including search results from different parent folders. Its Open command opens a single folder in the current browser, launches selected folders in separate companion windows, and sends selected documents to their registered Shell handlers. Desktop and namespace browser Delete requests from one parent use that provider's native Shell delete verb. Mixed-parent selections queue all `IShellItem` entries in a single `IFileOperation`, preserving recycle/undo behavior for Delete and permanent removal for Shift+Delete. Mixed-parent filesystem selections open one merged native Properties sheet; selections with virtual Shell items retain provider-native item Properties. If Shell notifications cannot be registered on the desktop, Desktop Tuner logs the failure and retains filesystem watchers plus manual refresh. In shell-host mode, the optional per-user “Open with Desktop Tuner” folder command forwards its path to the running shell's companion Explorer, avoiding an inert duplicate process. Win+B focuses the custom taskbar's system area; arrow keys navigate its controls, Enter activates one, and Escape returns to the previous app. Win+X opens a custom Power User menu with common administration tools, companion Explorer, Start search, Run, desktop, and power actions. Win+R opens the companion Run dialog, which launches parsed commands, keeps a clearable recent-command list, and routes folders and Shell namespace locations into Desktop Tuner's companion Explorer. Win+A, Win+N, Win+S, Win+Space, Win+W, and Win+Tab open Quick Settings, Notification Center, Windows Search, the keyboard-layout picker, Widgets, and Task View after both keys are released. For the first nine pins, Win+number activates the pin, Win+Ctrl+number activates its most recently active window, Win+Shift+number launches another instance, and Ctrl+Win+Shift+number requests an elevated instance when supported. Pinned folders launch in companion Explorer. Win+M minimizes eligible application windows and Win+Shift+M restores only the windows captured by that shortcut; these actions are separate from Win+D's companion-desktop toggle. The custom taskbar does not yet reproduce arbitrary notification-area extensions, Windows' native Start/taskbar relationship, or every shell flyout. CI can build the mode but cannot validate sign-in, recovery, Shell Launcher edition behavior, or display integration on a real Windows 11 desktop.

## Distribution gate

The repository has no production code-signing certificate. Windows requires the sparse identity package to be signed by a publisher certificate trusted on the target PC before it can be registered. The unsigned package produced for validation is not installable for normal users. Do not ship a self-signed development certificate or install one into a user's Trusted People store as a workaround.

Until a trusted publisher certificate is available, the installer keeps using the existing per-user registry verbs, which Windows may place under **Show more options**. After signing is provisioned, the release flow can sign `DesktopTuner.identity.msix`, install it for the current user with the app directory as its external location, copy the native DLL and manifest assets beside the app, and remove the package during uninstall. Registration and invocation then need verification on supported Windows 11 desktop builds.

The Explorer extension improves context-menu integration. It does not replace Explorer windows or the Start menu.

Custom taskbar app menus can show the Recent and Frequent Jump List categories through the Shell [`IApplicationDocumentLists`](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nn-shobjidl_core-iapplicationdocumentlists) API when a pinned Shell item or running app window exposes its AppUserModelID. Its [`GetList`](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-iapplicationdocumentlists-getlist) method exposes Recent and Frequent destinations; Windows does not make pinned destinations, custom categories, or task commands available through that API.
