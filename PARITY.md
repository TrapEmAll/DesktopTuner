# StartAllBack parity tracker

StartAllBack's public product description is the baseline: a classic-style Start menu, a redesigned taskbar, File Explorer and Control Panel styling, context-menu changes, and cross-app visual consistency. This tracker separates current companion-app behavior from remaining product gaps. “Implemented” describes Desktop Tuner features; it does not imply that Windows' built-in shell has been replaced or that a feature has passed interactive desktop validation.

## Validation and shell-integration notes

When selected Shell items come from different parent folders, Delete queues the full selection in one native `IFileOperation`; normal Delete requests undo/recycle behavior and Shift+Delete requests permanent deletion. Same-parent selections continue to use the provider's native Shell verb. For multiple filesystem-backed items from different folders, Properties opens one merged Shell property sheet; selections containing virtual items retain provider-native per-item Properties because `SHMultiFileProperties` requires filesystem parsing paths. These paths let heterogeneous desktop selections share native Shell operations where Windows supports them.

Custom taskbar app context menus expose the app's native Recent and Frequent Jump List destinations when its AppUserModelID is available from a packaged or filesystem pinned Shell item or a running window. Users can Ctrl-drag a folder onto an app pin to add a persisted Pinned destinations entry; the custom menu launches it through companion Explorer when shell-host routing applies. Windows' documented [`IApplicationDocumentLists`](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nn-shobjidl_core-iapplicationdocumentlists) API only enumerates Recent and Frequent destinations through [`GetList`](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-iapplicationdocumentlists-getlist); Windows-managed pinned destinations and custom categories remain outside the public reader API.

The companion Explorer maps mouse side buttons to Back and Forward in the active tab's folder history. Replacement-mode auto-hide registers edge-docked bars with the per-monitor AppBar API and releases the registration when disabled or closed; if an edge is already claimed, Desktop Tuner retains local auto-hide behavior. These code paths are covered by automated checks, but live reveal/collision behavior still needs Windows 11 desktop validation.

Windows [Shell Launcher](https://learn.microsoft.com/en-us/windows/configuration/shell-launcher/) can replace `Explorer.exe` as the logon shell on Enterprise, Education, and IoT Enterprise editions; it also removes Explorer's desktop shell. Desktop Tuner can configure and restore an isolated current-user Shell Launcher mapping when the optional Windows feature is already enabled and no existing mappings are present; it preserves the previous default and enablement state and uses Explorer for other accounts. Windows 11 Pro additionally supports Microsoft's per-user [Custom User Interface policy](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-winlogon#customshell), which starts an alternate interface instead of Explorer. Desktop Tuner detects its own configured executable and enters `--shell-host` mode; settings can set/restore that per-user policy on supported editions. The shell entry point runs a separate worker under a bounded supervisor, retries one failed start, and starts Explorer after a normal exit or exhausted retry. After repeated failure, it clears the per-user policy only if it still targets Desktop Tuner, preventing the same broken shell from being selected at next sign-in. These opt-in paths remain unvalidated at sign-in and recovery on live managed Windows desktops.

The all-edition `--shell-overlay` mode hosts the companion desktop, Start, and taskbars while Explorer remains in the background. It covers Explorer's main taskbar controls and exposes the native notification area on supported edge-aligned layouts. It is an overlay, not a Winlogon shell replacement; it does not replace Explorer windows or shell services and does not prevent Explorer from starting. Keep the Windows taskbar available until live recovery testing is complete.

The current Windows App SDK and Win32 public documentation do not expose APIs for replacing native taskbar internals or arbitrary built-in Start visuals. Those gaps need compatibility-tested shell integration and a Windows-build test matrix; registry toggles alone are insufficient. See [SHELL-INTEGRATION.md](SHELL-INTEGRATION.md) for setup, known limits, and recovery instructions.
